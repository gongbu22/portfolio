## 삼성물산 ITAM 자산관리시스템 TO-BE 전환 구축 프로젝트

### 1. 프로젝트 개요

| 항목 | 내용 |
|---|---|
| 프로젝트명 | 삼성물산 ITAM 자산관리시스템 TO-BE 전환 구축 프로젝트 |
| 수행 기간 | 2025.12 ~ 2026.06 |
| 담당 업무 | ITAM 화면 재구성 및 기능 구현, SLA 통계 시스템화 |
| 기술 스택 | E-GENE(플랫폼), JavaScript, JSP, Java, MariaDB |
| 협업 도구 | GitLab |


#### 프로젝트 소개

- 기존 X-Platform·Java 기반 ITAM 자산관리시스템을 E-GENE 플랫폼으로 전환하는 프로젝트입니다.
- 전산기기, 네트워크, 보안 등 기업의 IT 자산을 관리하는 시스템입니다.
- 사용자 요청부터 시스템 결재, 필요에 따른 SAP 결재 연동 및 결재승인여부에 따른 후속 처리까지하는 시스템입니다.
- 관리자는 접수된 요청 건을 조회하고 처리할 수 있으며, 자산별 관리 현황과 재고 수량, 입·출고 내역, I/F성공여부, 자산상태 등을 확인할 수 있습니다.
- 추가적으로 기존 수작업으로 관리하던 SLA 통계를 시스템화하기 위해 타 시스템의 근무시간 데이터를 API로 수집하고, 배치 처리하는 기능과 관련 화면을 구현했습니다.

### 3. 주요 개발 경험 및 성장

#### 3-1. 업무 프로세스 이해를 기반으로 한 TO-BE SQL 쿼리 수정

**경험 및 어려웠던 점**
- 현장 네트워크 신청부분을 구현할 때 
- AS-IS에서 TO-BE로 전환되면서 기존 2개의 테이블(신규, 이전/해지)이 하나로 통합되고, 업무 유형구분을 위한 신규 컬럼이 추가됨.
- 관리 화면에선 하나의 신규 등록건을 여러번 이전 신청 할 수 있었기 때문에 가장 최근 신청건만 조회되도록 SQL을 수정 필요
- 그리고 관리화면에선 관리자가 사용자의 신청정보에 추가 정보를 입력하고 처리하는 과정에서, 처리 상태에 따른 수정 가능여부와 요청 통계에 미치는 영향을 함께 고려해야했음

**해결 과정**
- 기존의 Tibero SQL 을 MariaDB에 맞게 변경
- 네트워크의 신규 등록 및 이전·해지 신청 유형에 따른 데이터 관계를 분석하고, 변경된 컬럼 구조를 반영해 SQL 쿼리 수정
- 기존 업무 프로세스와 TO-BE 플랫폼의 처리 흐름을 확인하여 화면별 데이터 처리 방식 파악
- 관리자 업무 특성과 처리 상태에 따른 수정 가능 여부를 고려해 워크플로우 단계 및 화면 처리 방식 검토

**배운 점**
- SQL을 단순히 데이터베이스 문법에 맞게 변경하는 것뿐만 아니라, 실제 업무 프로세스와 데이터 간의 관계를 이해해야 정확한 쿼리를 작성할 수 있다는 점을 배웠습니다.
- 하나의 업무를 담당할 때 사용자 뿐만 아니라 관리자 부분처럼 연관된 곳까지 생각하는 것이 필요하며, 큰 흐름을 파악하는 것이 중요하다는 것을 배웠습니다.

#### 3-2. 새로운 E-GENE 플랫폼의 특성 이해 및 ITAM 업무 적용

**경험 및 어려웠던 점**
- ITSM 업무 프로세스에 최적화된 e-gene 플랫폼에 기존 ITSM과는 다른 ITAM 자산관리 업무를 구현해서 추가해야하는 상황
- ITSM의 워크플로우 중심 구조와 ITAM의 업무 특성이 달라 기존 플랫폼 기능을 그대로 적용하기 어려운 부분 발생
- 예를 들어, 목록에서 바로 수정할 수 있는 기능적 제약으로 상세 화면을 별도로 구성해야했으며, ITSM의 워크플로우 중심 구조에 맞춰진 필수 컬럼과 데이터 처리 규칙을 ITAM 업무에도 고려해야 했음
- 일부 기본 컬럼이 누락되면 상세 화면이 정상적으로 열리지 않는 등 플랫폼 고유의 동작 방식에 대한 이해 필요

**해결 과정**
- 플랫폼 업체에서 제공하는 교육을 수강하며 기본 구조와 개발 방식 학습
- 업체에서 운영하는 개발자 질의응답 커뮤니티를 활용해 구현 과정에서 발생한 문제 해결
- 기존에 운영 중인 ITSM 소스 코드를 참고해 플랫폼의 구현 방식과 공통 기능 파악
- 프로젝트 중반부터 함께한 플랫폼 업체 직원에게 구현 방법을 문의하거나, 공식 홈페이지의 게시판을 통해 공통함수 및 기능에 대해 확인

**배운 점**
- 특정 업무에 특화된 플랫폼이라도 다른 업무 영역에 적용될 수 있으며, 이 과정에서 기존 프로세스와의 차이를 이해하는 것이 중요하다는 점을 배웠습니다.
- 동료 및 플랫폼 업체 담당자와 지식과 경험을 공유하며 소통하는 것이 혼자 고민하는 것보다 더 효율적으로 문제를 해결할 수 있었습니다.
- 문제 해결 과정에서 불확실한 부분은 플랫폼 업체 담당자에게 직접 문의하는 것이 정확하고 빠른 해결 방법이 될 수 있음을 경험했습니다.
- 플랫폼 버전에 따라 지원하는 기능과 적용 방법이 다를 수 있어, 문의 시 사용 중인 버전 정보를 함께 전달하는 것이 정확한 답변을 얻는 데 중요하다는 점을 알게 되었습니다.
